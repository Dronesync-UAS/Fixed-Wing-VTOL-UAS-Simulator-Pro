# Decisions Log Update — Native Ubuntu 24.04 Build Session

This covers everything needed to reproduce today's working PX4 + Gazebo
Harmonic setup from a fresh Ubuntu 24.04 install, including every fix
required along the way. Add this to the project decisions log so a future
rebuild (new instructor laptop, disk failure, etc.) doesn't have to
rediscover these the hard way.

## System

- **Ubuntu 24.04 LTS ("noble") exactly.** PX4 v1.15.4's bundled setup
  script does not know about 24.04 and will silently do the wrong thing
  (see below). Confirm with `lsb_release -a` before starting.
- Native install (not WSL) — WSL2's GPU passthrough breaks Gazebo's ogre2
  renderer on this hardware regardless of GPU detection. This was the
  original reason for moving off WSL.
- Linux username on this install: `uas-sim`, host `Getac-X600`.

## Step-by-step rebuild

1. `sudo apt update && sudo apt install -y git curl`
2. `git clone --branch v1.15.4 --recursive https://github.com/PX4/PX4-Autopilot.git`
3. In the cloned folder, before running setup:
   - `export PIP_BREAK_SYSTEM_PACKAGES=1` (Ubuntu 24.04 blocks system-wide
     pip installs by default; PX4's script needs this to proceed)
   - `export CMAKE_POLICY_VERSION_MINIMUM=3.5` (newer CMake rejects some of
     PX4's older CMakeLists.txt syntax without this)
4. **Replace the bundled setup script before running it:**
   ```
   curl -fsSL https://raw.githubusercontent.com/PX4/PX4-Autopilot/main/Tools/setup/ubuntu.sh -o Tools/setup/ubuntu.sh
   ```
   Reason: the v1.15.4-tagged version of this script pre-dates Ubuntu
   24.04. On 24.04 it (a) tries to install a Java version for jMAVSim that
   no longer exists as a package, causing a hard failure, and (b) even if
   that were fixed, it would install the *wrong, deprecated* Gazebo Classic
   rather than Gazebo Harmonic. The current `main` branch version of this
   *same file* correctly detects 24.04 and installs Harmonic with no Java
   dependency. This is a safe swap — it's a setup helper, not part of PX4's
   actual flight code, and the rest of the checkout stays pinned to v1.15.4.
5. `bash ./Tools/setup/ubuntu.sh --no-nuttx`
   (`--no-nuttx` skips the physical-flight-controller toolchain, which
   isn't needed for simulation-only work and also avoids an unrelated
   missing-package error on 24.04.)

## Required local code patch

**File:** `src/modules/simulation/gz_bridge/GZBridge.cpp`

PX4 hardcodes a 10-second wait for Gazebo's initial "clock" signal after
spawning the vehicle. This is too short for visually heavy worlds (confirmed
with Baylands) on this hardware, causing a reliable
`ERROR [gz_bridge] timed out waiting for clock message` failure and no
vehicle appearing.

**Fix (apply after cloning, before building):**
```
sed -i 's/int sleep_count_limit = 10000;/int sleep_count_limit = 60000;/' src/modules/simulation/gz_bridge/GZBridge.cpp
```
This extends the wait from 10s to 60s. Must be reapplied on any fresh
clone — it's a local workaround, not upstream PX4 behaviour.

## Running the simulator

```
make px4_sitl gz_standard_vtol_baylands
```

**Known gotcha — leftover background Gazebo processes:** if a previous
session's Gazebo didn't shut down cleanly (common if a run was interrupted
mid-load), a *headless* `gz sim ... -s` process can linger invisibly. The
next launch will silently reattach to it (log shows
`gazebo already running world: baylands`) instead of opening a visible
window, and previously-added changes (like the camera, below) can appear
to be "missing" simply because you're looking at an old orphaned instance.

**Fix, every time something looks stuck or a window doesn't appear:**
```
pkill -9 -f gz-sim-server
pkill -9 -f px4
```
Then relaunch. Checking `ps aux | grep -i "gz sim"` first (looking for a
line ending in ` -s`) confirms whether this is the cause.

## FPV camera on standard_vtol

Added a forward-facing camera sensor directly onto the aircraft's existing
`base_link` (as a sibling of the existing navsat/magnetometer sensors) in:
`Tools/simulation/gz/models/standard_vtol/model.sdf`

Inserted right after the existing `navsat_sensor` block:
```xml
<sensor name="fpv_camera" type="camera">
  <gz_frame_id>base_link</gz_frame_id>
  <pose>0.25 0 0 0 0 0</pose>
  <camera>
    <horizontal_fov>1.74</horizontal_fov>
    <image>
      <width>1280</width>
      <height>960</height>
    </image>
    <clip>
      <near>0.1</near>
      <far>3000</far>
    </clip>
  </camera>
  <always_on>1</always_on>
  <update_rate>30</update_rate>
  <visualize>true</visualize>
</sensor>
```

**Note:** an earlier attempt following PX4's own documented pattern (a
separate `mono_cam` model merged in via a joint, matching how PX4's
`x500_mono_cam` is built) reliably failed with a Gazebo frame-graph error
(`Child frame ... not found in model`) on this Gazebo version, even though
it's the officially documented method. Attaching the camera sensor directly
to an existing link, as above, avoids that error entirely and is the
approach that works.

**Known limitation — no live video in QGroundControl.** The camera sensor
itself works correctly (confirmed via Gazebo's own Image Display GUI
panel — Gazebo menu (⋮) → "Image Display" → topic
`/world/baylands/model/standard_vtol_0/link/base_link/sensor/fpv_camera/image`).
However, streaming that feed into QGroundControl (with the telemetry HUD
overlay) is **not currently possible** — this is an acknowledged, open gap
in PX4's own Gazebo Harmonic integration (`GstCameraSystem`/camera
streaming is not yet functional for this simulation pathway, per PX4's own
docs and open GitHub issue #22563 on PX4-Autopilot), not something fixable
locally. Current workaround: view the raw feed via Gazebo's Image Display
panel alongside QGroundControl's normal instrument readouts.

## Open/deferred decision

The original decisions log specifies the simulator runs **headless** (no
3D GUI) for students in the final deployed package, to avoid depending on
student laptop GPU hardware. **This is being deferred, not reversed:** for
now, active development/testing continues with the full 3D GUI visible (as
used throughout this session). Producing an actual headless build for
student delivery remains a separate, later packaging step — not yet done.

## QGroundControl (authoring machine)

Installed via the official AppImage method for Ubuntu 22.04/24.04:
```
sudo usermod -a -G dialout $USER
sudo apt-get remove modemmanager -y
sudo apt install gstreamer1.0-plugins-bad gstreamer1.0-libav gstreamer1.0-gl -y
sudo apt install libfuse2 -y
sudo apt install libxcb-xinerama0 libxkbcommon-x11-0 libxcb-cursor-dev -y
# log out and back in for the dialout group change to apply
wget https://d176tv9ibo4jno.cloudfront.net/latest/QGroundControl-x86_64.AppImage
chmod +x QGroundControl-x86_64.AppImage
./QGroundControl-x86_64.AppImage
```
