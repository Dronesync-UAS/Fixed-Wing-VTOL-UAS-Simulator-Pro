# Arming readiness in the top bar — 11 October 2026

## The problem

The console showed `Status: Disarmed` and nothing else. That same two words
covered two completely different situations:

- the aircraft is fine, nobody has armed it yet
- PX4 is actively refusing to arm and has a specific reason

The instructor could not tell them apart, so the response to a refused ARM
was to press ARM again. From the session log:

```
WARN  [health_and_arming_checks] Preflight Fail: Yaw estimate error
WARN  [health_and_arming_checks] Preflight: GPS Vertical Pos Drift too high
WARN  [health_and_arming_checks] Preflight Fail: Yaw estimate error
```

PX4 was saying exactly what was wrong, to a terminal nobody was reading —
and when the simulator is started from the console's **Load Environment**
button there is no terminal at all, only `~/uas_sim_logs/sim_launch.log`.

## Where the answer comes from

`HEARTBEAT.system_status`. PX4 v1.15.4,
`src/modules/mavlink/streams/HEARTBEAT.hpp` lines 107–127:

```c
uint8_t system_status = MAV_STATE_UNINIT;

if (vehicle_status.arming_state == vehicle_status_s::ARMING_STATE_ARMED) {
        system_status = vehicle_status.failsafe ? MAV_STATE_CRITICAL : MAV_STATE_ACTIVE;
} else if (vehicle_status.calibration_enabled || ...) {
        system_status = MAV_STATE_CALIBRATING;
} else if (vehicle_status.pre_flight_checks_pass) {
        system_status = MAV_STATE_STANDBY;
}
```

The first line is the part worth writing down. When the aircraft is disarmed
and its preflight checks are **not** passing, none of the branches fire and
PX4 reports `MAV_STATE_UNINIT`. The name says "uninitialised", which reads
like PX4 is still booting; it is in fact the "ARM will be refused" state,
and it is the state the console most needed to show.

`MAV_STATE` values are from the MAVLink spec (`minimal.xml`): 0 UNINIT,
1 BOOT, 2 CALIBRATING, 3 STANDBY, 4 ACTIVE, 5 CRITICAL, 6 EMERGENCY,
7 POWEROFF, 8 FLIGHT_TERMINATION.

Both were read out of the source, not recalled.

## What was built

`simulator_link.py` now keeps three fields alongside the rest of telemetry:

| field | meaning |
|---|---|
| `arm_ready` | `True` / `False` / `None` before the first heartbeat |
| `arm_state` | short label — `Ready to arm`, `Not ready`, `Armed`, … |
| `arm_blocker` | PX4's own sentence, from `STATUSTEXT` |

The reason text comes from `STATUSTEXT` lines beginning `Preflight`,
`Arming denied` or `Arm denied`. PX4 repeats these for as long as the
condition holds, which is what makes them usable: a line seen in the last
15 seconds is the live reason, an older one is history and is dropped
(`_ARM_BLOCKER_MAX_AGE_S`). A reason is also cleared the moment PX4 reports
the checks passing — a complaint that is no longer blocking anything should
not still be on screen.

The top bar gained an **Arming** cell next to **Status**: green
`Ready to arm`, amber while waiting for the first heartbeat, red
`Not ready - Yaw estimate error`. The redundant `Preflight Fail:` prefix is
stripped for display and the full sentence stays in the tooltip.

## Deliberately not done

**No automatic retry, and no "arm when ready" button.** The right response
to a failing preflight check is to wait for the estimator to converge, not
to have software hammer the command until one gets through. Showing the
reason is the fix; the instructor decides what to do about it.

**The readout does not try to list every check.** PX4 has a structured
arming-check report, but it is not in the MAVLink stream the station reads.
`system_status` plus the `STATUSTEXT` line is what is actually available,
and it answers the question that was being asked.

## Testing

`tools/test_arm_readout.py` encodes real `HEARTBEAT` and `STATUSTEXT`
messages and pushes them through `simulator_link._read_one_message()` —
the station's own reader, not the mapping in isolation. It covers all nine
`MAV_STATE` values the mapping knows, an unknown value, the newest reason
replacing an older one, a stale reason being dropped, an unrelated
`STATUSTEXT` being ignored, `reset_flight_state()` clearing the readout, and
`/telemetry` staying JSON-serialisable. All pass.

`tools/offline_render_check.py` gained an arming-readout section so the page
wiring is checked on every future edit, and its stub telemetry dict was
updated to match the real one. Passes.

**Not yet seen in the simulator.** The logic is tested against real MAVLink
messages, but no one has watched the cell go red and then green against a
running PX4. That is the next thing to confirm.
