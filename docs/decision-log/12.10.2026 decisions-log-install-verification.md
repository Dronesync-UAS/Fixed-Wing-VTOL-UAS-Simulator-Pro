# Two verifiers: is this machine actually set up?

12 October 2026

## What was asked

> "now i need you to give me some scripts to veryfy that everything has
> been installed correctly from all results achieved today"

## The thing worth writing down

Everything built on this project lives in one of two places, and the
difference is the cause of nearly every "it isn't there" of the last
fortnight:

**In the repository.** `git pull` brings it: the modules, the plugins, the
world files, the checks.

**Outside the repository.** A tool has to be run once, per machine:

| What | The tool | Where it writes |
|---|---|---|
| The four legs | `tools/aircraft_legs_apply.py` | `~/PX4-Autopilot/.../standard_vtol/model.sdf` |
| The gimbal, its camera, the rangefinder | `tools/gimbal_apply.py` | the same file |
| The chase boom | `tools/chase_angles_apply.py` | the same file |
| Satellite imagery | `tools/fetch_satellite.py` | `sim/worlds/satellite/` (gitignored) |
| The Mapbox token | by hand | `~/.mapbox_token` |

A `git pull` cannot put legs on the aircraft. Both verifiers are
organised around that split, and say which group each failure is in.

## Two scripts, not one

`tools/verify_install.py` needs nothing running. It is the one to run
after a pull, or on a machine that has never been set up.

`tools/verify_live.py` needs PX4, Gazebo and the station all up. It reads
Gazebo's topic list and asks the station the same questions the browser
asks it.

Splitting them means the first one is always runnable. A single script
would have had half its checks permanently reporting "cannot tell", which
is the state in which people stop reading output.

## Decisions

### Every failure carries its own fix

Not "the gimbal is missing" but "the gimbal is missing" followed by
`python3 tools/gimbal_apply.py`. The failures are then printed again at
the end, numbered, one command each, in the order to run them - because
the person running this is an instructor and "work out which tool does
that" is not a reasonable thing to ask of them.

### A camera that is installed but silent looks exactly like one that is
not installed

So the live script distinguishes them. For the joint controllers it uses
`gz topic -i` rather than the topic list, because a
`JointPositionController` subscribes rather than publishes: its topic
does not appear in `gz topic -l` until something has published to it, so
the list alone would report every working controller as missing.

### Both end by saying what they could not check

A row of green OKs is not a statement that the simulator looks right. The
nose camera can be publishing upside down; the gimbal can point at the
sky; a widened world can have a seam at the horizon. Each script closes
with the list of things that need eyes, so the output cannot be mistaken
for more than it is.

### The token is never printed

Only whether the file is there and whether its permissions are owner-only.
`verify_install.py` fails the check if the file is group- or
world-readable, and the fix it prints is `chmod 600 ~/.mapbox_token`.

## Where it stands

`verify_install.py` was run here and behaves correctly: it passes
everything in the repository, passes all eleven offline checks, and
correctly reports the two things this container genuinely does not have
(no `gz`, no PX4 checkout).

`verify_live.py` was tested against a stand-in `gz` command and a
stand-in station serving the real endpoint shapes - every branch of it,
pass and fail, including the no-Gazebo and no-station paths. It has never
been run against real Gazebo or real PX4, because neither is reachable
from here. If a topic name has drifted in a way the stand-in copied
faithfully from `sim_target.py` but Gazebo spells differently, this is
where that would show.
