# One icon instead of two terminals — 11 October 2026

## What starting a session used to take

1. open a terminal, `tools/start_world.sh blackrock`
2. wait for the build
3. open a second terminal, `GCS_WORLD=blackrock python3 instructor_station.py`
4. open a browser at `localhost:8080`

Four steps across three windows, before any teaching happens. And step 3
repeats the world name from step 1 by hand — get them different and the
station's Gazebo controls (freeze, reposition, wind, camera) address a world
that isn't running. Nothing errors. The buttons just quietly do nothing,
which reads as broken software rather than a typo.

## What replaced it

`tools/uas_launcher.py`, and two desktop icons that call it:

```
python3 tools/uas_launcher.py              # last used training area
python3 tools/uas_launcher.py blackrock    # a specific one
python3 tools/uas_launcher.py --stop
python3 tools/uas_launcher.py --status
```

`tools/install_launcher.sh` puts **UAV Academy Simulator** and **Stop UAV
Academy Simulator** in the applications menu (Super, type "UAV"), optionally
on the Desktop too. No sudo — `~/.local/share/applications` is the per-user
half of the desktop-entry spec.

The world is chosen once and passed to both halves, so step 1 and step 3 can
no longer disagree. That is the actual fix; the single icon is the
convenience on top of it.

## Decisions worth recording

**No GUI toolkit.** The obvious build is a small tkinter window with a
dropdown and a Start button. tkinter is not installed by default on Ubuntu,
and a launcher that fails to launch because its own window toolkit is
missing is worse than no launcher at all. The desktop entries use
`Terminal=true` instead, so progress appears in a window with nothing to
install.

**It prints what it is doing.** A first build of PX4 takes minutes. A silent
icon that may or may not be working is worse than a window saying
`[3/5] still starting (45s)... first build can take minutes`.

**It watches for PX4's ready line, it does not sleep.** The launcher reads
`~/uas_sim_logs/sim_launch.log` until it sees
`Startup script returned successfully`, or `ninja: build stopped` /
`make: ***`, or the process exits. Sleeping a fixed number of seconds would
report success on a build that had already died, and the next half-hour goes
on hunting for a simulator that was never there.

**A listening port is not a running station.** `wait_for_station` asks for
`/connection_status` and wants HTTP 200, because something else holding 8080
would otherwise be reported as ready and the console would open a dead page.

**It starts both detached, and stopping is a separate icon.** Keeping the
launcher in the foreground as a supervisor would be tidier, but then closing
that window by accident ends a lesson in progress.

**`--stop` clears `/tmp/px4*` as well as killing the processes.** The same
glob `tools/start_world.sh` uses. PX4's lock files outlive a Ctrl+C, and the
next launch then dies with "PX4 server already running for instance 0",
which says nothing about the real cause.

## Testing

`tools/test_launcher.py` drives the real orchestration against a stand-in
PX4 (a one-line Makefile) and a stand-in station (an HTTP server answering
`/connection_status`): ready-line detection and that it is prompt rather
than a timer, build failure reported as a failure, timeout naming the log, a
listening-but-silent port rejected, a real station accepted, a station that
dies reported rather than hung on, an unknown training area refused by name,
and no-argument falling back to the remembered world. All pass.

`tools/install_launcher.sh` was run against a throwaway `HOME` and the
generated `.desktop` files inspected; `--remove` leaves nothing behind.

**Not yet run against real PX4.** Everything above is the launcher's own
logic. That it brings up the actual simulator on the actual machine is the
one thing these tests cannot show.

## The camera starts on the aircraft (added later the same day)

*"when gazebo starts the aircraft is not in view, i have to select follow to
find it."*

Expected, in hindsight. The aircraft is a few metres across and the terrain
is 16 km wide, so a camera left wherever the world last put it is pointing at
empty desert far more often than not. Every session began with hunting for
the aircraft.

The launcher now does it: once the Gazebo window advertises its camera
services it sets the follow target and a rear-and-above offset, the same
`/gui/follow` plus `/gui/follow/offset` pair the console's **Set External
View** uses, through the same `gazebo_view` helper rather than a second
copy of the logic.

**The wait is the whole trick.** `/gui/follow` is served by the GUI process,
not the simulation server, and the GUI comes up well after PX4 reports ready.
Call it too early and it fails *silently* - the request returns fine and
nothing moves, which is indistinguishable from the feature not existing. So
the step polls `gz service -l` for `/gui/follow` first, for up to 90 seconds.

**And it is never fatal.** If the camera services never appear, the launcher
says so, points at the Camera panel, and carries on. A session with the
camera in the wrong place is still a session; a launcher that refuses to
finish because a camera was slow is not.

12 m and rear-above, matching the console's Camera panel defaults, so the
launcher and the panel agree rather than fighting each other.

`tools/test_launcher.py` covers both halves: that it gives up rather than
hanging when the GUI never appears, and that once the GUI is up it sets the
follow target *before* the offset - which matters, because the offset
service ignores a request with no target set.
