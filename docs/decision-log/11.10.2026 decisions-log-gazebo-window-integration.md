Gazebo window alongside the GCS — tiled now, native app recorded as a later phase (11 October 2026)

**Question asked:** can the GCS have an integrated window for the Gazebo simulation?

**Answer: not truly embedded, and the reason is structural.** The instructor station is an HTML page
served over HTTP and shown either in a browser or a pywebview window. Gazebo's GUI is a native
Qt/OpenGL application. Neither a browser nor a pywebview window can host a native OpenGL window
inside the page. This is not a Gazebo limitation or a missing setting - it is what the station
currently is.

**Options considered:**

1. **Tile the two windows side by side** - chosen. `tools/tile_windows.sh` positions the station
   and the Gazebo window to a configurable split of one screen. Looks like a single console, keeps
   full mouse control of the Gazebo view, costs nothing to render, and depends on nothing external.
   Needs `wmctrl` (`sudo apt install wmctrl`); without it, GNOME's own Super+Left / Super+Right
   does the same by hand with nothing to install. Kept as its own script rather than folded into
   `start_training_area.sh`, which lives outside this repo and launches the simulator - a
   window-arranging convenience must not be able to stop the sim starting.

2. **Chase camera streamed into a GCS panel**, the way the FPV feed works. Genuinely inside the
   page, but costs a second rendered camera on hardware already recorded as marginal (12 July
   entry), and the view becomes a picture with no mouse look. Still available if wanted.

3. **Gazebo's own web visualization** - rejected. Checked rather than assumed: gz-sim 8 (Harmonic)
   ships no websocket server; that only arrives in gz-sim 10 (Ionic). On Harmonic it lives in the
   separate `gz-launch` package, and the client is Gazebo's **hosted** page at
   app.gazebosim.org/visualization, which needs an internet connection and is documented as beta
   with self-hosting undocumented. A training station that must work offline should not depend on
   someone else's website being up.

**Recorded as a possible next phase, after the GCS is tested and working as it is:** rewriting the
station as a native desktop application. That is the only route to a genuinely embedded Gazebo
view - a native Qt or GTK window can host the Gazebo render widget, which an HTML page cannot.

Worth knowing before that is costed:
- **What it would unlock:** a single-window console with the 3D view embedded, no second window
  to arrange, and direct access to the render camera rather than driving it over services.
- **What it would cost:** the entire UI is currently HTML/CSS/JS inside `instructor_station.py` and
  would be rebuilt. The parts that are *not* UI - `simulator_link.py` (MAVLink), `video_feed.py`,
  `event_logger.py`, the whole `plugins/` folder and its loader - are already separate from the
  page and should carry over largely unchanged. That separation is worth protecting in the
  meantime: anything new belongs in a plugin or a module, not in the page.
- **Sequencing:** do it after the current station has been through real instructor use, not
  before. The present version is still finding out what instructors actually want on screen (the
  adjustable layout and the external views both came out of first contact with it), and those
  answers are cheaper to discover in HTML than in a native rewrite.
