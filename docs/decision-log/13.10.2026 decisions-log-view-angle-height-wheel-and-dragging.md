# 13 Oct 2026 - A locked view angle, a wheel on the height tape, and dragging

Three things asked for in one go. They are unrelated except that all three
are about the instructor setting the console up the way they want it and
finding it that way tomorrow.

## 1. The external view's angle - Settings > Aircraft

A reading in degrees, an up and a down arrow, and a LOCK button. The
arrows move the camera at once so the angle can be judged by eye; LOCK
writes it down and every session from then on opens at it.

**Only the Behind view changes.** Top and Low exist precisely to be
different angles; forcing one figure on all six would leave a row of
buttons that all did the same thing. `gimbal.set_behind_elevation()`
rewrites that one preset and nothing else.

**Clamped to the joint's own travel**, -28 to +83 degrees, in three
places: the arrows disable at the ends, `chase_view()` clamps what it is
given, and `read_prefs()` clamps again on the way back off disk. The last
one matters because the file can be edited by hand, and a boom told to go
to 500 degrees would sit at its stop while the console claimed otherwise.

**It works on the ground and in the air alike**, which was asked for and
is free: the boom is a camera mount and the flight controller knows
nothing about it.

A bug was found while building this. `/chase_view` with no query defaulted
to the Behind preset, so the console reading its own state at start-up
would have swung the camera back to Behind on every browser refresh - an
instructor watching from Top would have lost the view each time they
reloaded. There is now a read-only mode, `?read=1`.

## 2. The mouse wheel over the m AGL tape

Pointer on the height tape, spin to climb or descend. 5 m a notch,
clamped to the 5-120 m that `plugins/climb_to.py` enforces anyway.

The tape is painted on a canvas, so there is no element to hang a
listener on. The rectangle the gauge drew it in was already published as
`cv.tapeRects` for the tests, and the hit test uses those same figures -
so the live area is exactly the tape that is visible, and it stays correct
when the instructor drags a corner tile over it and the gauge steps the
tapes inboard.

**One command per burst.** A wheel notch is a repeat event; sending per
notch would put a dozen altitude changes on the wire for one flick. The
target moves on screen immediately and goes out 450 ms after the wheel
stops, which is also what makes it safe to overshoot and come back.

It counts from the height the aircraft is at, not from zero - otherwise
the first notch from 60 m would command a descent to 5 m.

The wheel event is consumed. Without that the console scrolls under the
pointer while the height is being changed, which moves the tape itself.

## 3. Dragging every container

Most of this already existed and had since 12 Oct: the two rails, the two
corner tiles and every pop-up panel - Settings among them - already
dragged and were remembered in `~/uas_sim_logs/gcs_layout.json`.

The one container still nailed down was the **external view strip**. It
now has a grip and is dragged like the rest.

It becomes FIXED to the window on the first grab rather than staying
positioned against the view. Two reasons: left and top mean different
things in the two cases, so a strip dragged without the switch jumps on
the first pixel; and the view itself travels into a 400 px corner tile
when another view is made the main one, which would take the strip with
it.

## Where the settings live

`~/uas_sim_logs/gcs_layout.json`, under a new `prefs` key beside the
existing `console` one. Same file, so one backup carries both, and
separate keys so saving a layout cannot wipe the angle or the other way
round - which is checked, because it is the obvious way this breaks later.

## Testing

`tools/test_payload.py` gained sections 8b, 12, 13 and 14 - thirty-odd
checks covering the clamping at both ends and on disk, start-up applying
the locked angle, the other presets being left alone, a corrupt layout
file not stopping the station, the wheel's hit area and arithmetic, and
the strip following the mouse exactly rather than jumping.

**playwright was installed to get this coverage.** Both browser checks -
`test_console_browser.py` and `test_flight_display.py` - had been silently
skipping for want of it, which for a change that is almost entirely
JavaScript meant the offline checks were proving very little. Installed
into the user site with `pip install --user --break-system-packages`,
because this Ubuntu marks its Python as externally managed; that keeps it
in `~/.local` and out of the OS packages. The browser build came from
`python3 -m playwright install chromium`.
