Deep audit of the station (11 October 2026)

Run with authorisation to fix what it found. Everything below was verified from the code, with
automated checks added where the class of bug could recur. Nothing here needed the simulator.

## Fixed

**Every MAVLink control fired blind.** Twenty-two of them. Not one checked the COMMAND_ACK,
although `simulator_link.send_command_and_wait` had existed all along. A command PX4 refused was
indistinguishable from one it obeyed - which is why "the commands do not respond properly" took an
afternoon to pin down: the station could not tell the instructor anything, because it never asked.
All now report accepted, refused with PX4's reason, or no acknowledgement, several with the likely
cause attached.

**Failure toggles lit their status light even when PX4 refused.** The console could show a failure
the aircraft did not have - worse than no light at all on an assessment console. The state is now
left alone unless PX4 took the command.

**Reset Scenario repositioned an aircraft it had failed to disarm**, and reported a completed
reset. It now stops and says why.

**Both reset buttons used a fixed spawn height** of 615.5 m - Hoggar's old value. On Black Rock,
whose playa is at 1.3 m, either would have teleported the aircraft to 615 m. The height now comes
from the environment list.

**Switching environment kept the previous world's track and home point.** The plan view showed two
worlds at once, and range-from-home - which drives the CAP722B range limit - was computed against a
point that could be thousands of kilometres away. `simulator_link.reset_flight_state()` clears it
on every switch.

**The event log had no thread safety.** The HTTP server handles each request on its own thread and
the telemetry loop logs student responses from another; two unsynchronised appends can interleave
inside a row. This file is the CAP722B assessment record. Now serialised by a lock - verified with
eight threads writing 200 rows each, 1600 rows, none malformed.

**The event log raised on failure.** It is called from the telemetry thread, so a full or read-only
disk would have taken telemetry down mid-exercise. It now reports to the console and continues:
losing a log row is bad, losing telemetry is worse.

**One bad message ended telemetry for the session.** The loop had no exception handling, so a
missing field on a message variant - or that log write failing - killed the only reader of the
MAVLink socket, and the console froze on its last values with no indication why. Each message is
now handled in isolation.

**The camera never reconnected after a world switch**, because the subscription was made before the
new simulator existed. A watchdog re-subscribes when frames stop or the topic stops matching.

**Panels stretched to the tallest in their row** - `align-content` was set, `align-items` was not -
which undid every fit and forced the scrolling and manual resizing.

**The station started silently alongside another one**, leaving the browser talking to the old
instance. It now refuses and says so.

## Added so these cannot return

- `tools/audit_commands.py` - calls every control with PX4 stubbed to refuse and to stay silent,
  and fails if any claims success or lights its status dot anyway.
- `tools/check_worlds.py` - parses every world file and reports what each declares.
- Both pass, alongside the existing `tools/offline_render_check.py`.

## Found and deliberately not changed

**The four `MAV_CMD_INJECT_FAILURE` controls** - Data Link Loss, Engine Failure, RC Signal Loss,
Motor Failure. The 10 August entry documents that command as accepted-but-ineffective on this PX4
version, which is why the GPS proxy exists. They now report PX4's acknowledgement, and their source
says plainly that accepted is not the same as effective. Each needs one live test with a recorded
result before an instructor is told it works.

**Toggle GPS Failure** depends on `~/UAS-Academy/Archive/instructor_panel/gps_dropout_proxy.py`
still being at that path, and reports success on launching the script rather than on effect. A
moved file would look like a working button that does nothing.

**The EKF warnings** - `Preflight Fail: Yaw estimate error` and
`Preflight: GPS Vertical Pos Drift too high` - appear in every world, block arming, and are the
reason takeoff was refused. The corrected magnetic field did not clear them. This is a PX4
estimator question, not a station one, and it is the main open item.
