# 13 Oct 2026 - The ground that had no texture

## What was seen

The seven plane worlds had never been loaded in Gazebo; their own headers
said `NOT YET RUN`. The coast world was opened for the first time and its
ground came back with no texture at all - and, stranger, a DIFFERENT
colour from each camera, captured at the same moment:

| camera  | the ground |
| ------- | ---------- |
| payload | blown-out white, pixel variation 0.0 |
| nose    | muddy brown, rgb(173,150,143), variation 6.4 |
| chase   | near-black, rgb(22,38,49), variation 0.0 |

Ground cannot change colour with viewpoint. The valley world, measured in
the same scene, came back at variation 22.2 - properly textured.

## What it actually was

**PBR `<albedo_map>` does not render in this Gazebo Harmonic / ogre2
build.** It produces a near-black surface.

Proven by spawning boxes side by side into the RUNNING world - same light,
same texture file, one variable each:

| material on the box | result |
| ------------------- | ------ |
| plain `<diffuse>` colour | lit and shaded, correct |
| `<albedo_map>` | near-black |
| `<albedo_map>` + normal + roughness | near-black |
| `<albedo_map>` by absolute path | near-black |
| `<emissive_map>`, same file | renders the texture |

That explains everything that did not add up. The valley's terrain is a
heightmap with 240 m of relief, which goes through Gazebo's TERRAIN
shader and its own `<texture><diffuse>` - not the PBR path. The sky dome
is right because it uses `emissive_map`. The 220 km far plane is right
because it uses a plain colour and no maps.

## Three fixes that were wrong, and why

1. **The heightmap image was degenerate** - every one of its 16,641 pixels
   was 0, so minimum equalled maximum. Real, and worth having fixed; not
   the cause.
2. **The visual had no `<material>`** - also true, also not the cause.
3. **A mesh instead of a heightmap** - `tools/make_ground_mesh.py`, with
   UVs that tile. Still not the cause.

Each was a plausible reading of the symptom. None of them had been tied to
the object.

## The test that should have come first

`ground_near` was removed from the world entirely and the simulator
restarted. The chase camera measured `rgb(22,38,49)` - **byte-identical to
every previous run.**

That figure had been constant all day: through the flat heightmap, the
real height range, the explicit material, the mesh, the plain colour, and
finally with the object deleted. **`ground_near` has never been visible
from that camera.** Every change was aimed at a surface that was not in
the picture.

One question - "does changing this alter the result at all?" - is one
restart, and it belonged before three rewrites.

## Where it was left

* `tools/plane_ground_texture.py` writes a MESH with a plain lit colour
  and no texture maps. That is the one configuration proven to render, and
  it is what the far plane has always used. It is not claimed to fix the
  dark ground, because it has not been shown to be visible.
* `tools/make_ground_mesh.py` builds the mesh: 8 km square, exactly flat,
  UVs that tile. Flat matters - the collision is a separate box at z=0, so
  relief in the visual would show the aircraft sunk into the ground.
* The degenerate heightmap is fixed in `tools/make_surface_maps.py`
  regardless, and `tools/test_surface_maps.py` no longer asserts the
  degenerate case.

## Still open

**What the dark surface actually is.** It is either the 220 km
`ground_plane` or the sky dome's lower hemisphere. Both are testable the
way `ground_near` was: remove one, restart, see whether the number moves.
Two restarts.

Note for whoever does it: a runtime-spawned 8 km mesh does NOT render in
this build - three "experiments" that way proved nothing, and it only
showed up because the measurements came back identical to three
significant figures. Spawned BOXES do render, and are a sound way to test
a material.

## The standing lesson

Measure the premise before changing anything, and treat "the change made
no difference" as the answer rather than as a reason to try the next
mechanism.
