# 14 Oct 2026 - The student's ground station was flying the instructor's display

Found by flying the aircraft from the new console rather than by reading
code, which is the only reason it was found at all.

## The symptom

The instructor's top bar showed **"Mode 0.0"** instead of a flight mode,
and at the same time showed **ARMED while the aircraft sat disarmed on the
ground**. It came and went about once a second, so it read as a glitch.

It had been seen the night before and written off as "transient", because
asking the station a moment later always gave the right answer. That was
the wrong call: it was not a transient, it was a 1 Hz corruption that
happened to be invisible between two polls.

## What it actually was

Listening directly on the station's own MAVLink port, with everything
running as it normally does:

    sys=1   comp=1    type=22  custom_mode=50593792  base_mode=29   armed=False  x20
    sys=255 comp=190  type=6   custom_mode=0         base_mode=192  armed=True   x21

Two senders, both at 1 Hz. The first is the aircraft (main 4, sub 3 -
Hold / Loiter). **The second is QGroundControl**: system 255, component
190 is QGC's own identity on the wire, type 6 is MAV_TYPE_GCS, and its
base_mode 192 is the ARMED and MANUAL_INPUT bits together.

The station's reader took every heartbeat it received and decoded it as
the aircraft. So QGC's heartbeat set `armed = True` (that is bit 128 of
base_mode, which QGC sets for its own reasons and which means nothing
about the vehicle) and decoded custom_mode 0 as main mode 0, sub mode 0 -
a mode that does not exist, printed as "Mode 0.0".

**This is not an edge case in this project, it is the normal condition.**
The whole design decided yesterday is that the student flies standard
QGroundControl and the instructor watches this station. QGC is therefore
always running, always on the link, and was always corrupting the
instructor's display.

## Why it was nearly missed twice

The aircraft and QGC heartbeat at the same rate, so whichever arrived last
won. Any single reading had a coin-flip chance of being right, and the
checks that were run - including a direct query that returned a perfectly
correct answer - landed on the right side of the flip.

Reproduced deliberately, on the old code, by sending one GCS heartbeat
into the station's port: armed went True, mode went "Mode 0.0", and stayed
that way. On the new code the same injection changes nothing.

## The fix

Only the aircraft's own heartbeat drives the display. QGroundControl
v5.1.5 solves this in `MultiVehicleManager::_vehicleHeartbeatInfo` with
two filters, and the same two are used here rather than inventing a rule:

* ignore any component that is not `MAV_COMP_ID_AUTOPILOT1`;
* ignore the `GCS`, `ONBOARD_CONTROLLER`, `GIMBAL` and `ADSB` vehicle
  types.

Measured after the change, with QGC running and heartbeating: mode held
"Hold / Loiter" and armed held False across eight consecutive readings.

## The test that now covers it, and the trap in writing it

`tools/test_arm_readout.py` sections 11-13: a QGC heartbeat must not touch
the mode, the armed flag or the arm readout; a gimbal's must not either;
and the aircraft must still get through afterwards.

Writing it exposed something that would have made the test worthless. The
harness built its messages with `heartbeat_encode()` and never packed
them - and an unpacked message reports **system 0, component 0**, because
the source ids are only written during `pack()`. A filter on the sender
would have rejected those messages too, so every existing section would
have failed, and a filter loose enough to let them through would not have
caught the real bug. The harness now packs, which is also what a message
off the wire always is.

## One other thing this turned up

`tools/verify_install.py` was still checking for `nav_port` - a wing light
removed on 13 Oct on instruction, because the wing lights were wrong and
were not wanted. So a clean machine reported a fault and told whoever ran
it to re-apply a part that had been deliberately taken off. It now checks
`nav_tail`, the tail light that replaced them, which flashes green with
GPS and red without.

## What is NOT claimed

The GPS-loss failsafe was measured on the way to this and behaves
correctly - with the failure injected in the hover PX4 went to main 4 sub
6 (Land) with system_status 5 (CRITICAL), which is a real failsafe
descent. That was observed once, in one world, at 20 m. It is not a
tested statement about how PX4 responds to GPS loss in general.
