External ("chase plane") aircraft view (11 October 2026)

**Requested:** a full view of the aircraft from behind and above, with fixed alternatives
(top-down, sideways, front) and a manual view - so the instructor can see what the student's
aircraft is actually doing, not just the nose camera.

**How it is done.** A "Set External View" control in the Camera panel: pick a viewpoint from a
drop-down, set a distance, press the button. It drives the camera in the **Gazebo window** via
Gazebo's own services, the same technique already proven for freeze and reposition.

Confirmed against gz-gui 8's `CameraTracking` source rather than assumed:
- `/gui/follow` (`gz.msgs.StringMsg` -> `gz.msgs.Boolean`) - sets which model the camera follows,
  by name. An **empty name releases the camera**, which is how the manual view works: the mouse
  then flies the view freely in the Gazebo window.
- `/gui/follow/offset` (`gz.msgs.Vector3d` -> `gz.msgs.Boolean`) - where the camera sits relative
  to the aircraft. The offset is in the **aircraft's own frame** (gz-gui's `trackWorldFrame`
  defaults to false), so the view rotates with the aircraft and "rear and above" stays behind it
  through a turn. gz-gui's own default of `(-3, 0, 2)` - behind and above - is where the sign
  convention comes from: -x behind, +y left, +z above.
- The offset request is **ignored unless a follow target is already set**, so the two calls always
  go out in that order. Found in the source, not by trial and error.

**This build does not have the newer service.** `gz service -l` on this machine (gz 8.15.0) lists
`/gui/follow` and `/gui/follow/offset` but not `/gui/track`. The newer `/gui/track` with
`gz.msgs.CameraTrack` (which adds FOLLOW_FREE_LOOK and FOLLOW_LOOK_AT modes) is the eventual
replacement and does the same job - noted in `gazebo_view.py` so a future Gazebo upgrade that
drops the deprecated pair is a small change, not a re-investigation.

**Offsets scale with the distance box** rather than being hard-coded in metres, so one number
drives every viewpoint. At 20 m: rear and above `(-18, 0, 7)`, top-down `(-3, 0, 20)`, left side
`(0, 18, 5)`, right side `(0, -18, 5)`, front `(18, 0, 5)`. Top-down keeps a small rearward bias
deliberately - a camera directly overhead has no stable idea of which way is up.

**Rejected alternative: extra camera sensors streamed into a GCS panel**, the way the FPV feed
works. It would put the view inside the station page on one screen, which is tidier, but it costs
a second rendered camera on a machine whose performance is already recorded as marginal (12 July
entry), and manual free-look would have to be built from scratch when Gazebo already has it. Worth
revisiting if the station ever needs to run without the Gazebo window visible.

**Framework change:** `plugin_loader`'s input contract now supports `"type": "select"` with
`options`, for a choice from a fixed set rather than a quantity. Documented in the loader's
docstring alongside the existing number-box inputs. Number inputs are unchanged.

**Not yet confirmed:** no flight flown with this. The service calls and the offset arithmetic are
verified, but how well each viewpoint frames the aircraft in practice - whether 20 m is the right
default, whether top-down needs more rearward bias - needs one session with it. Adjust the
fractions in `gazebo_view.py`'s `VIEWS` table from what it looks like on screen.
