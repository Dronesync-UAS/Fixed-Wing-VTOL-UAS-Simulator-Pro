# Two copies of every world, and nothing copied one to the other

12 October 2026

## What happened

`verify_live.py`, run on the instructor's machine within an hour of being
written, reported Gazebo up with **4 topics**, no cameras, and the world
loaded as `training_area` while the station expected
`training_area_nullarbor`. Following that back found two separate faults
and one wrong conclusion of mine.

### A Gazebo server from the previous day

```
uas-sim 356522 5 Oct11 ? 01:31:19 gz sim --verbose=1 -r -s .../training_area_blackrock.sdf
```

Started Oct 11, still running. The world file on disk was modified Oct 12
at 00:01 - **after** that process started - so the running server was
holding the file's older content, whose `<world name>` was still
`training_area`. I first read this as the file on disk being stale. It was
not; the process was.

### The real fault: the worlds that fly are a different set of files

`~/PX4-Autopilot/Tools/simulation/gz/worlds/` held five world files:
`training_area`, `blackrock`, `nullarbor`, `uyuni`, `flat_test`.

`sim/worlds/` in this repository held twelve, and the five with the same
names were two to three times larger - 38 KB against 11 KB for Black Rock
- because every tool here edits the repository's copies.

So:

* **Six training areas added on 11 Oct had never been installed.** They
  could not be flown at all. `start_world.sh` did not list them either.
* **`far_ground_apply.py` widened the repository's copies.** Of the seven
  it changed, only `flat_test` was reaching the simulator, because
  `start_world.sh` happened to copy that one file on its way past.
* The same was true of every earlier world edit: scenery, sky, magnetic
  field, weather. What reached Gazebo depended on whether the tool had
  been pointed at PX4's tree that day.

### And my own verifier had the same blind spot

`verify_install.py` checked `sim/worlds/`. It reported all twelve worlds
healthy and widened while six of them were not installed and could not be
flown. A verifier that checks the wrong copy is worse than no verifier,
because it is believed.

## Decisions

### One install step, and the launcher runs it

`tools/install_worlds.py` copies every `sim/worlds/*.sdf` and every media
file any world refers to into PX4's tree. `start_world.sh` runs it before
launching and refuses to launch if it could not install everything.

Media travels with the worlds because a world whose heightmap is missing
loads as an empty void with no error saying why.

### It refuses rather than overwriting something newer

If the copy in PX4's tree is newer than the repository's, that is
somebody's local edit - probably an older tool pointed at PX4's tree -
and losing it silently is worse than refusing. `--force` overwrites, and
a `.preinstall` backup is kept either way.

### The verifier now checks the copies that load

`verify_install.py` compares the two sets and distinguishes three states:
not installed at all, installed but older than the repository's, and
installed but newer. Each has a different fix and the third is the one
that needs reading before acting.

### `start_world.sh` lists all twelve

With spawn heights and relief from `sim_target.py`, which measured them
from each world's own ground, rather than typed again here.

## Where it stands

`tools/test_install_worlds.py`, 24 checks, all against a temporary
folder - the real PX4 tree is never written by the test. It covers the
install, the no-op second run, the dry run, the refusal with its backup,
`--force`, the out-of-date case, a world that does not parse, and that
`start_world.sh` lists every environment the station offers.

`install_worlds.py` itself was exercised here against a stand-in PX4
tree: install, refusal, `--force`, `--revert`, and byte-for-byte
comparison of an installed world and an installed heightmap.

Never run against a real PX4 tree or a real Gazebo. Nobody has yet
watched a freshly installed world load, and the six new training areas
have still never been flown.
