# 12.10.2026 - The stacked-view bug, number steppers, full-height columns,
# and Mapbox

All of these came from a screenshot. Every one was reproducible once
somebody looked.

## The bug behind three of the complaints

"messages remain permanent on screen obstructing comand panels" and
"panel at the top over other panls" and "gimbal camera view not found"
were all one fault.

`applyHero()` moves the views between the main screen and the two corner
tiles with `appendChild`, which MOVES an element. With three views and
three slots, every view was re-parented on every swap, so nothing could
ever be left behind. The payload view made it four views and three
slots - and the one that is neither the hero nor in a corner was simply
never touched.

So: select Payload, then Chase. `#hero` now holds BOTH. The payload view
is invisible itself, but its control strip is a `#hero > .view > .paybar`
and so is its canvas - and both were drawn on top of the chase picture
and over the left-hand controls. The "TARGET LOCK" and "1.0x 60 deg FOV"
text written across the bottom of the screen was the payload reticle's
last painted frame: a canvas keeps its pixels, and the redraw loop had
stopped, so nothing was ever going to clear it.

Two lines fix it - park every view that is not in a slot back into the
hidden store - and `tools/test_console_browser.py` now walks six view
changes and checks that exactly one view is on the main screen and at
most one control strip is showing. The reticle is also cleared when the
payload view stops being the hero, so a stale frame cannot come back.

**And a second one found on the way**: `CONSOLE_HEROES` never contained
"payload", so choosing the payload view was saved, rejected on the way
back in, and the console reopened on the chase view every single time.

## The number boxes have arrows again

"any number figure that can be changed, use up and down arrows as
before as typing is taking too long."

Fair. The native spinners were removed this morning because they sat
INSIDE the box and clipped the third digit - "100" came out as "10C".
The answer was not to leave the arrows off; it was to draw them beside
the box instead, where they cannot overlap the value.

They are twice the size of the native ones, which matters on a
touchscreen, and they **accelerate while held**: one press is one step,
and holding runs through the range, getting faster to a floor of 45 ms.
Going from 20 m to 400 m is now a held button rather than forty clicks.
`stepUp()`/`stepDown()` are the browser's own, so each control's min,
max and step are honoured without this code knowing any of them.

The rails had to get wider to hold them - 132 to 166 px - which exposed
the next fault.

## One rail width, in one place

The rail width was written out in `applyLayout` and again as a magic
`142` in `home()`, where the corner views are placed. Widening the rails
changed one of them, so the corner views moved underneath the right-hand
rail and covered the message panel.

There is now a `railWidth()` and a `railEdge()`, and the browser check
measures for overlap between every rail and every corner view at three
screen sizes in both layouts.

## The columns fill the screen

"both colums must apppear from the start covering the entire available
screen space even if some of it is empty (more functions to come)."

The rails were already docked full height in the code. What the
screenshot showed was a SAVED arrangement: the rails had been dragged
and resized at some point, and a floating rail keeps the height it was
dragged to - so the left column stopped halfway down with no obvious way
back.

`CONSOLE_VERSION` now sits in the saved layout. A layout saved under an
older version is dropped rather than half-applied, once, and the console
comes up on the current defaults. The check measures both columns
against the available height at three screen sizes.

## The settings window had 200 px of nothing in it

Not reported, but visible in the same screenshot. When the settings
window gained categories down the side, the old single-column rule -
`.win-body.settings { flex-direction: column }` - was left in the sheet
BELOW the new one, so it won. The category list and the panes stacked
vertically instead of sitting side by side, and the first setting was
200 px down an otherwise empty window.

`tools/test_payload.py` now checks that the categories are beside the
panes and that the first setting is within 30 px of the top.

## The payload view says what to do

"gimbal camera view not found." Partly the stacking bug above, and
partly that the gimbal has to be added to the aircraft once with a tool.
The blank payload view now prints the exact commands - the tool to run,
and the `gz topic -l` to check with - and the topic it is actually
listening on, which is the one fact that turns "it is blank" into
something diagnosable.

## Mapbox

Asked for mid-change. Added to `tools/fetch_satellite.py` as two more
providers beside the existing USGS and Esri ones:

* **`mapbox`** - Mapbox Satellite. Global, high resolution.
* **`mapbox-outdoors`** - roads, paths and place names rather than
  imagery, which is what is actually wanted half the time when briefing
  an area.

Three decisions worth recording:

* **It cannot be the default,** because it needs an access token and
  USGS and Esri do not. A station whose default needs a sign-up is a
  station that fails for the next person.
* **It refuses before it downloads.** No token means a message naming
  where to get one and offering the keyless provider instead - not a
  run of 404s halfway through sixteen tiles.
* **The token is never written down.** It comes from `--token` or
  `MAPBOX_TOKEN` and goes into the request only. It is not in the cached
  image's sidecar, because a token in a file that gets copied between
  machines is a token that leaks. The check asserts that.

One technical note: Mapbox serves 512 px tiles on the `@2x` endpoints. A
512 px tile covers the same ground as four 256 px ones, so these
providers go in at a zoom level lower - same detail, a quarter of the
downloads - and the stitcher now takes the tile size from the provider
rather than assuming 256. It also resizes any tile that comes back the
wrong size, because a service quietly serving 256 when 512 was asked for
would otherwise leave gaps in the grid.

**Never run.** Mapbox is not reachable from the machine this was written
on, so the download path has not executed. The provider table, the token
handling, the refusal and the zoom arithmetic are checked by
`tools/test_terrain_fetch.py`.
