# 12.10.2026 - auditing every control against the PX4 source

## Why

An instructor reported that the controls did not work: LOITER flew the
aircraft away in a straight line, FORWARD FLIGHT refused from a 20 m
hover with no way to climb, and pressing ARM made the aircraft take off
and crash. Those three are symptoms of four separate faults. Rather than
patch each symptom, every control was read against the PX4 v1.15.4 source
it talks to.

The rule throughout: a parameter is only correct if the PX4 source says
so. Nothing below is from memory or from a documentation page; each
finding names the file and the lines.

## What was wrong

### 1. ARM flew the aircraft (fixed in 0f34756)

ARM sent `COMPONENT_ARM_DISARM` and nothing else, so whatever mode PX4
had been left in took effect the moment it armed.

`Commander.cpp` lines 1035-1045: `VEHICLE_CMD_NAV_TAKEOFF` does nothing
but change the mode intention to `AUTO_TAKEOFF`. That mode outlives a
failed attempt. PX4's own `commander takeoff` (lines 338-344) sends the
takeoff and then a *separate* arm command - so arming is what starts the
climb.

ARM now switches to HOLD first whenever the mode would fly on arming.

### 2. TAKEOFF aimed at the Atlantic (fixed in 23503b4)

`navigator_main.cpp` lines 622-631:

    if (PX4_ISFINITE(cmd.param5) && PX4_ISFINITE(cmd.param6)) {
            rep->current.lat = cmd.param5;
            rep->current.lon = cmd.param6;
    } else {
            // If one of them is non-finite set the current global position
            rep->current.lat = get_global_position()->lat;

The station sent `0` for both. Zero is finite, so every takeoff was
commanded to latitude 0, longitude 0. NaN is the way to say "here".

Whether this also explains the aircraft stopping at about 10 m when 20 was
asked for is **not established**.

### 3. LOITER flew a straight line, not a circle

`FlightTaskOrbit.cpp` line 170, in `activate()`:

    _center = _position;

and lines 296-300:

    position_to_center_xy = center2d - Vector2f(_position);
    closest_point_on_circle = Vector2f(_position)
        + position_to_center_xy.unit_or_zero()
          * (position_to_center_xy.norm() - _orbit_radius);

The station sent NaN for the centre, which means "here". With the centre
on the aircraft, `position_to_center_xy` is a sub-metre scrap of estimator
noise. `unit_or_zero()` turns that into a unit vector on an arbitrary
bearing, and `(norm - radius)` is approximately minus the whole radius -
so the target lands one radius away in a direction decided by nothing.
The aircraft flies a straight line to it.

The centre is now computed: one radius off the right wing, so the aircraft
is on the circle from the first instant.

The speed was wrong too. Lines 72-75 only overwrite the speed when the
value is finite, so NaN left PX4 on the 1 m/s that `activate()` sets - a
quarter of an hour per lap of a 150 m circle.

### 4. The failure injections had never worked

All four sent a failure unit that is not a defined value: 10 for the
motor, 13 for RC, 14 for the data link. PX4 v1.15.4
`msg/VehicleCommand.msg` lines 130-144, matching MAVLink's own
`FAILURE_UNIT` enum, puts the system units at 100 and up:

    uint8 FAILURE_UNIT_SYSTEM_BATTERY = 100
    uint8 FAILURE_UNIT_SYSTEM_MOTOR = 101
    uint8 FAILURE_UNIT_SYSTEM_SERVO = 102
    uint8 FAILURE_UNIT_SYSTEM_AVOIDANCE = 103
    uint8 FAILURE_UNIT_SYSTEM_RC_SIGNAL = 104
    uint8 FAILURE_UNIT_SYSTEM_MAVLINK_SIGNAL = 105

A comment in those files claimed the numbers had been "cross-checked
against MAVLink's own enum definitions". They had not been. This is the
lesson of the whole exercise: a comment saying something was checked is
not evidence that it was.

They are also gated behind `SYS_FAILURE_EN`, which is 0 by default -
`failure.cpp` lines 163-171 refuses outright when it is not 1. The station
now reads that parameter and says so.

### 5. A background script that did not start still said it had

`start_background_script` reported "<name> started." whatever happened.
The scripts are launched as `python3 <path>`, and python3 exists even when
the path does not - so the process launched, exited immediately, and the
button reported success. The GPS failure control is launched this way.

It now checks the file exists, keeps the script's output in
`~/uas_sim_logs/<name>.log`, waits half a second, and reports the last
line if the script has already died.

## What was added, and why it belongs here

* **CLIMB / DESCEND TO.** There was no way to change height in flight. The
  climb box only worked from the ground. `MAV_CMD_DO_CHANGE_ALTITUDE`
  (186) is documented by PX4 itself as a reposition with only the altitude
  set (`navigator_main.cpp` line 417), takes the height above *sea level*
  in param1, and needs the aircraft armed (line 412).

* **FORWARD FLIGHT as a whole departure.** Refusing below 40 m was
  correct - the aircraft trades height for airspeed during the transition
  - but refusing was all it did. It now climbs to the transition height on
  a straight run, transitions, then climbs away. `DO_REPOSITION` needs bit
  0 of param2 set or Commander answers UNSUPPORTED without acting
  (`Commander.cpp` lines 748-753); PX4 denies an MC-to-FW transition in
  Takeoff, Land, RTL and Orbit (`vtol_att_control_main.cpp` lines
  171-178), so the sequence leaves those modes first.

* **A hard reset on NEW SESSION.** Gazebo's models are reset, not its
  clock: `all: true` would wind simulation time back to zero underneath a
  running PX4. PX4 is also asked to reboot, and a POSIX build will refuse
  - `Commander.cpp` lines 1217-1226 put the reboot behind
  `#if defined(CONFIG_BOARDCTL_RESET)`, which a SITL build does not have.
  The attempt is made so the answer is known rather than assumed.

## What is still not known

* None of this has been flown. Every change is read off the source.
* Whether the null-island takeoff target is what capped the climb at 10 m.
* Whether `SYS_FAILURE_EN` is already 1 on the instructor's machine.
* Whether a model-only Gazebo reset upsets PX4's estimator in practice.
