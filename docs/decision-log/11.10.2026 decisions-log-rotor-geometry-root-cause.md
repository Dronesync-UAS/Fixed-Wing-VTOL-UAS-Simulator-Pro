VTOL attitude instability — root cause found: rotor geometry overwritten (11 October 2026)

**The 22 August instability is explained.** `param show -c` on the live PX4 shows all eight rotor
position parameters saved as non-default values:

| Parameter | Airframe 4004 default | Saved on this machine | Error |
|---|---|---|---|
| `CA_ROTOR0_PX` | 0.1515 | 0.3500 | 19.8 cm |
| `CA_ROTOR0_PY` | 0.2450 | 0.3500 | 10.5 cm |
| `CA_ROTOR1_PX` | -0.1515 | -0.3500 | 19.8 cm |
| `CA_ROTOR1_PY` | -0.1875 | -0.3500 | 16.2 cm |
| `CA_ROTOR2_PX` | 0.1515 | 0.3500 | 19.8 cm |
| `CA_ROTOR2_PY` | -0.2450 | -0.3500 | 10.5 cm |
| `CA_ROTOR3_PX` | -0.1515 | -0.3500 | 19.8 cm |
| `CA_ROTOR3_PY` | 0.1875 | 0.3500 | 16.2 cm |

The standard_vtol's asymmetric rotor layout has been replaced with a generic symmetric 0.35 m
square. PX4's control allocator derives each motor's roll, pitch and yaw authority from these
positions, so with the wrong geometry the mixing is wrong: motors run unevenly, attitude control is
poor, and the aircraft departs on takeoff. That is precisely what the 23 August entry describes -
"armed, spun all 4 propellers unevenly, then disarmed itself" and "takeoff attempts resulted in
uncontrolled spinning" - and what was seen again on 11 October as lifting a metre, drifting forward
and striking the ground.

**Why every previous theory failed.** These live in PX4's saved parameter file, not in any world,
so they followed every test: the custom terrain, the flat test world, Black Rock, and - decisively
- the stock PX4 default world, which the 22 August entry used as evidence that the terrain was not
at fault. It was right about the terrain and wrong about what that proved.

The startup banner has been reporting it all along: `BSON document size 824 bytes, decoded 824
bytes (INT32:19, FLOAT:20)` - 39 saved overrides, on every single launch, in every log pasted
today.

**Likely origin:** 0.35 m arms are plausible for the MFE Fighter modelling work rather than the
stock standard_vtol. Set during that work, saved, and never cleared.

**The fix**, at the `pxh>` prompt:

    param reset CA_ROTOR0_PX CA_ROTOR0_PY CA_ROTOR1_PX CA_ROTOR1_PY CA_ROTOR2_PX CA_ROTOR2_PY CA_ROTOR3_PX CA_ROTOR3_PY
    param save

then restart the simulator so the airframe re-applies its own defaults.

**Two other non-default parameters worth resetting at the same time:** `FW_USE_AIRSPD 0` and
`SYS_HAS_NUM_ASPD 0` disable airspeed use, which matters in the fixed-wing phase and is not an
airframe default.

**A bug of this project's own, found in the same list:** `COM_MOT_TEST_EN` reads `1065353216`,
which is the bit pattern of the float 1.0. The motor-test plugins sent a float while declaring
`MAV_PARAM_TYPE_INT32`, so PX4 reinterpreted the bits. Fixed by packing the integer into
`PARAM_SET`'s float field.

**Lesson for the record.** Five explanations were proposed and discarded today - terrain
misalignment, camera placement, missing Gazebo systems, the magnetic field, wind left on - before
anyone read the list of parameters that differ from default. That list took one command and would
have pointed here immediately. When a fault follows the aircraft across worlds, restarts and
rebuilds, look first at what persists across worlds, restarts and rebuilds.

## The saved values fit neither aircraft

Checked after the question "the current aircraft V shape has 4 motors and 1 pusher" - which is the
stock `standard_vtol` layout, and also the MFE Fighter's. The saved 0.35 m square matches neither:

| | PX (fwd/aft) | PY (lateral) |
|---|---|---|
| Stock standard_vtol (what is being flown) | ±0.1515 | ±0.245 / ±0.1875 |
| MFE Fighter, from this repo's own `model.sdf` | +0.400 / −0.467 | ±0.428 |
| **Saved on the machine** | **±0.3500** | **±0.3500** |

So it is a generic placeholder, not a deliberate setting for either airframe. Resetting to the
airframe defaults is right while the stock `standard_vtol` is the model being flown.

## When the MFE Fighter model is flown, these parameters must change with it

The control allocator must describe the aircraft actually being simulated. From this repo's
`sim/models/mfe_fighter/model.sdf`, converted from Gazebo's FLU frame (x forward, y **left**, z up)
to PX4's FRD convention (x forward, y **right**, z down) - so `PY_px4 = -Y_gazebo` and
`PZ_px4 = -Z_gazebo`:

| Model link | Gazebo (x, y, z) | PX4 (PX, PY, PZ) |
|---|---|---|
| `motor_1` | 0.400, −0.428, −0.042 | 0.400, 0.428, 0.042 |
| `motor_2` | −0.467, 0.429, 0.085 | −0.467, −0.429, −0.085 |
| `motor_3` | 0.400, 0.428, −0.042 | 0.400, −0.428, 0.042 |
| `motor_4` | −0.467, −0.429, 0.085 | −0.467, 0.429, −0.085 |
| `motor_f` (pusher) | −0.463, 0.000, −0.014 | −0.463, 0.000, 0.014 |

**Not to be applied blind.** Which model link corresponds to which `CA_ROTOR<n>` depends on the
actuator assignment in PX4's Actuators configuration, and each rotor's spin direction
(`CA_ROTOR<n>_KM` sign) has to match the model's joint axis. Confirm both against QGroundControl's
Actuators tab before flying, exactly as `motor_test_1.py`'s own docstring advises for output
numbering. The numbers above are the geometry; the mapping is a separate question.

This is also the lesson of the whole episode in miniature: a parameter set that does not describe
the aircraft being flown produces a flyable-looking aircraft that will not fly, and nothing in the
simulator will say so.

## Confirmed fixed (11 October 2026)

With the eight `CA_ROTOR*` parameters reset to the airframe defaults and the simulator restarted,
the aircraft took off vertically and held a stable 10 m hover in `training_area_blackrock`. The
uneven propellers, the one-metre lift followed by a forward departure, and the uncommanded
spiral are gone.

**The 22 August VTOL attitude instability is closed**, with a cause: PX4's control allocator had
the wrong rotor geometry, so its mixing did not match the aircraft. Not terrain, not the camera,
not missing Gazebo systems, not the magnetic field, not wind.

## Why ARM then TAKEOFF appeared to do nothing

Reported alongside the fix: pressing ARM and then TAKEOFF does nothing two or three times, then
pressing TAKEOFF on its own works. Two separate effects, neither a fault in the station:

1. **PX4 disarms itself about 10 seconds after arming if no takeoff follows**
   (`COM_DISARM_PRFLT`). Arming and then reaching for TAKEOFF often misses that window, so the
   takeoff arrives at a disarmed aircraft. `Disarmed by auto preflight disarming` appears in the
   logs each time it happened today.
2. **The preflight checks are still settling just after start-up** - `Yaw estimate error`,
   `height estimate not stable`, `GPS Vertical Pos Drift too high`. While any of them is failing,
   arming is refused, so both ARM and TAKEOFF do nothing. Repeated attempts eventually succeed
   because the estimator has had more time to converge, not because the repetition helps.

**So TAKEOFF alone is the correct action**, and it is what QGroundControl's own takeoff button
does: one command that arms and climbs together, leaving no window for the auto-disarm. ARM is for
checking the aircraft will arm, not a required first step.

**Practical guidance for instructors:** wait until the console stops printing preflight warnings -
roughly 30 to 60 seconds after the simulator starts - then press TAKEOFF once. Since the
acknowledgement fix earlier today, a refusal now says so on the station's status line with PX4's
reason, rather than appearing as a dead button.
