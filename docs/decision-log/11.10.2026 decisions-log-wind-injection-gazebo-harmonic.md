Wind injection in Gazebo Harmonic — transport confirmed working (11 October 2026)

Replaces the standing "live wind control in this version of Gazebo is unreliable per community
reports" caution that had `plugins/wind_gust.py` parked as a placeholder. Wind can be set at
runtime on this setup. What was unreliable was adding it blind; the mechanism itself is sound.

**What was wrong with the obvious approach.** Gazebo Harmonic (gz-sim 8.15.0 on this machine)
loads its default set of world systems *only if the world SDF declares none of its own* —
`SimulationRunner.cc`: "No systems loaded from SDF, loading defaults". The four
`training_area*.sdf` worlds each already declare 8 systems (Physics, UserCommands,
SceneBroadcaster, Sensors, Imu, AirPressure, NavSat, Contact). Had they declared none, adding a
single WindEffects `<plugin>` would have suppressed all of PX4's defaults — physics, IMU, GPS,
camera — and broken the sim rather than adding wind. Checked before editing, via
`tools/wind_survey.py`.

**Confirmed working end-to-end:**
- `<wind>` element (zero velocity) plus the `gz::sim::systems::WindEffects` plugin added to all
  four `training_area*.sdf` worlds by `tools/wind_apply.py`. Each file backed up to
  `.sdf.prewind`, re-parsed as XML after editing, auto-restored on failure.
- `/world/training_area/wind` appears after restart and accepts `gz.msgs.Wind` commands.
- The plugin's own `/world/training_area/wind_info` service (request `gz.msgs.Empty`, reply
  `gz.msgs.Wind`) reads the commanded value back — 20 m/s commanded, 20 m/s reported. The
  instructor → Gazebo path is proven, not assumed.
- `plugins/wind_gust.py` rewritten as a real control: two instructor inputs (speed in m/s,
  direction in degrees true that the wind comes FROM), toggle back to calm, status light,
  event logged via `log_instructor_action` for the CAP722B assessment record.

**Plugin tuning values** (`time_for_rise`, `sin`, `noise`) are copied from gz-sim8's own
`examples/worlds/wind.sdf`, not chosen by us. They shape how wind ramps and gusts; speed and
direction come from the instructor at runtime. Initial wind is zero, so an untouched sim flies
exactly as it did before this change.

**Not yet confirmed — still filed as experimental:**
- No flight has been flown with wind set, so how strongly the aircraft actually responds is
  unobserved. Gazebo's `LiftDrag` system does subtract wind from the airspeed vector, so the
  wings should feel it without needing per-link `<enable_wind>` — but "should" is not "seen".
  Deliberately not adding `<enable_wind>` to the airframe links: WindEffects would then apply a
  separate mass-based body force on top of the aerodynamic one, which risks double-counting on a
  lifting surface.
- The direction convention is reasoned from the world's ENU frame, not measured. One flight
  settles it: wind from 270 should push the aircraft EAST. If it goes the wrong way, the fix is
  the sign of x/y in `_wind_vector`.
- Move the plugin out of "Experimental - In Development" once both are observed.

**Visibility and precipitation: no mechanism exists in Harmonic.** Checked directly, not assumed
— gz-rendering8 has no fog API at all (`<scene><fog>` is in the SDF 1.11 spec but nothing renders
it), and there is no precipitation system among gz-sim8's 70-odd systems. The only candidate is
`particle_emitter`, which is visual and whose effect on the FPV camera feed is unknown. Treated
as a separate question rather than bundled in with wind.

**Separate observation, not acted on.** These worlds load 8 systems; PX4 upstream's own default
list also includes AirSpeed, Magnetometer and ApplyLinkWrench. A fixed-wing VTOL without the
AirSpeed system is worth a look alongside the open attitude-instability issue from 22 August. No
evidence of a connection — flagged for checking, not claimed as a cause.
