Missing Gazebo world systems — experiment for the VTOL attitude instability (11 October 2026)

**Observation, found while adding wind.** The four `training_area*.sdf` worlds each declare 8
Gazebo world systems: Physics, UserCommands, SceneBroadcaster, Sensors, Imu, AirPressure, NavSat,
Contact. PX4's own default list (`PX4-gazebo-models/server.config`) carries 13. Three of the
missing ones are **AirSpeed**, **Magnetometer** and **ApplyLinkWrench**.

**Why they are missing rather than inherited.** gz-sim8 loads its default system set only when the
world SDF declares none of its own - `SimulationRunner.cc`: "No systems loaded from SDF, loading
defaults". These worlds do declare systems, so PX4's list is never consulted, and whatever the
worlds leave out simply is not loaded. This is the same mechanism that made the naive wind-plugin
edit dangerous, seen from the other side.

**Why it is worth a flight.** The open issue from 22 August is a VTOL that arms, climbs, holds for
3-10 seconds, then enters an uncommanded spiral with "Attitude failure (roll)" / "(pitch)" and
failsafes. A fixed-wing VTOL running with **no simulated airspeed sensor** is worth ruling out.

The 22 August entry records that the same failure reproduced on the stock, unmodified PX4 default
world, which was taken at the time as evidence that the custom terrain was not at fault - and it
was. But at this submodule pin the stock worlds also declare their own systems, so they would carry
the same gap. That observation does not clear the systems; if anything it is consistent with them.

**This is a hypothesis with a plausible mechanism, not a diagnosis.** No flight has been flown with
the systems added. `tools/add_world_systems.py` adds them to all four worlds, with backups to
`.sdf.presystems`, XML validation, automatic restore on failure, and `--revert`. It also checks
whether each plugin's shared library is actually installed, since a world naming a plugin Gazebo
cannot load logs an error and carries on without it.

Adding systems to a world that already declares some is additive and carries none of the
suppression risk that applied to the wind plugin - there are no defaults left to suppress.

**Either result is worth having.** If the instability changes, the cause is found after two months.
If it is identical, revert and the question is closed cheaply. Record the outcome here either way.
