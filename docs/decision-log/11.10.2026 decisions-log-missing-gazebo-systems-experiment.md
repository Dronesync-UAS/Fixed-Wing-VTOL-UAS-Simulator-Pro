Missing Gazebo world systems — experiment for the VTOL attitude instability (11 October 2026)

**Observation, found while adding wind.** The four `training_area*.sdf` worlds each declare 8
Gazebo world systems: Physics, UserCommands, SceneBroadcaster, Sensors, Imu, AirPressure, NavSat,
Contact. PX4's own default list (`PX4-gazebo-models/server.config`) carries 13. Three of the
missing ones are **AirSpeed**, **Magnetometer** and **ApplyLinkWrench**.

**Why they are missing rather than inherited.** gz-sim8 loads its default system set only when the
world SDF declares none of its own - `SimulationRunner.cc`: "No systems loaded from SDF, loading
defaults". These worlds do declare systems, so PX4's list is never consulted, and whatever the
worlds leave out simply is not loaded. This is the same mechanism that made the naive wind-plugin
edit dangerous, seen from the other side.

**Why it is worth a flight.** The open issue from 22 August is a VTOL that arms, climbs, holds for
3-10 seconds, then enters an uncommanded spiral with "Attitude failure (roll)" / "(pitch)" and
failsafes. A fixed-wing VTOL running with **no simulated airspeed sensor** is worth ruling out.

The 22 August entry records that the same failure reproduced on the stock, unmodified PX4 default
world, which was taken at the time as evidence that the custom terrain was not at fault - and it
was. But at this submodule pin the stock worlds also declare their own systems, so they would carry
the same gap. That observation does not clear the systems; if anything it is consistent with them.

**This is a hypothesis with a plausible mechanism, not a diagnosis.** No flight has been flown with
the systems added. `tools/add_world_systems.py` adds them to all four worlds, with backups to
`.sdf.presystems`, XML validation, automatic restore on failure, and `--revert`. It also checks
whether each plugin's shared library is actually installed, since a world naming a plugin Gazebo
cannot load logs an error and carries on without it.

Adding systems to a world that already declares some is additive and carries none of the
suppression risk that applied to the wind plugin - there are no defaults left to suppress.

**Either result is worth having.** If the instability changes, the cause is found after two months.
If it is identical, revert and the question is closed cheaply. Record the outcome here either way.

## Result (11 October 2026, same day)

**Flown in the flat test world with the three systems added and the magnetic field corrected: no
flying issues.** Aircraft armed, took off, held at ~10 m in Hold/Loiter with 10 satellites, FPV
feed and flight-path plan view both live. The uncommanded spiral and the repeating "Attitude
failure (roll/pitch)" did not occur.

Direct evidence the AirSpeed system was the missing piece, from the PX4 startup log:

    INFO [airspeed_selector] No airspeed sensor detected. Switch to non-airspeed mode.
    INFO [airspeed_selector] Airspeed sensor healthy, start using again (-1, 1)

PX4 found an airspeed sensor where it previously had none. A fixed-wing VTOL running in
non-airspeed mode is a plausible and sufficient mechanism for the attitude failures seen since
22 August.

**Two changes were made together**, so strictly the credit is shared and not yet separated:
the three systems, and the magnetic field (which fixed the arming-blocking yaw estimate error).
The yaw error blocked arming rather than causing in-flight instability, so the systems remain the
likelier cause of the spiral - but if it matters, reverting only `fix_magnetic_field.py` would
separate them.

**Still to confirm** before calling this closed for training use: repeat takeoffs, a transition to
forward flight, and the same test in `training_area` once its terrain alignment is fixed - the
flat world removes variables the real training world still has.

## Retraction: the three systems do not reach PX4 at all (11 October 2026, later)

**The hypothesis in this entry was wrong, and the "result" above should not be relied on.**

Read from PX4 v1.15.4's own source rather than inferred:

- `src/modules/simulation/gz_bridge/GZBridge.cpp` subscribes to exactly five Gazebo topics: clock,
  world pose, IMU, odometry, air pressure, airspeed and navsat. **There is no magnetometer
  subscription anywhere in the file** - the string "mag" does not appear in it outside the licence
  header.
- The airframe this setup runs, `ROMFS/.../4004_gz_standard_vtol`, sets:

      param set-default SENS_EN_GPSSIM 1
      param set-default SENS_EN_MAGSIM 1
      param set-default SENS_EN_ARSPDSIM 1

  PX4 generates the magnetometer, GPS and airspeed **inside itself**, from ground-truth attitude
  and its own world-magnetic model, not from Gazebo sensors.

So:

- **The Magnetometer system added to the worlds is inert as far as PX4 is concerned.**
- **The AirSpeed system is inert too.** The stock `standard_vtol` model has no `airspeed_link`, and
  PX4 subscribes to a topic that does not exist; the "No airspeed sensor detected / Airspeed sensor
  healthy" pair in the log is `SENS_EN_ARSPDSIM` starting up, not the Gazebo system. That log line
  was read as confirmation of the hypothesis. It was not evidence of it.
- **`ApplyLinkWrench` is unrelated to sensing** and was inert from the start.
- **The magnetic-field correction does not reach PX4 either.** It is still right for Gazebo's own
  purposes - the previous values were sdformat's placeholder, wrong by up to 125 degrees of
  inclination - but it cannot have cleared a PX4 estimator warning, and the yaw error persisting
  afterwards is consistent with that rather than surprising.

**Therefore the 22 August VTOL attitude instability is NOT closed.** The clean flight recorded
above happened in the flat test world, and the likeliest explanation is that flat world, not these
systems. Erratic flight has since been seen again in Black Rock and in Hoggar.

**What this cost.** Three wrong explanations in one afternoon - a terrain misalignment, then the
camera, then these systems - each plausible, each disproved by a single measurement that was
available from the start. In this case the measurement was reading the bridge's subscription list,
which took two minutes.

**The changes are left in place** rather than reverted: they are harmless, and reverting would
restore backups taken before the magnetic-field correction, mixing two unrelated changes. But they
should not be described as a fix, and this entry is the record of that.

**Where to start next time:** `tools/px4_health_report.py` connects over MAVLink while the sim
runs and dumps the estimator and simulated-sensor parameters, PX4's own warnings, and live EKF,
GPS, vibration and attitude figures to `~/uas_sim_logs/px4_health_report.txt`. Run it before
theorising.

## Ground state measured, and it is healthy (11 October 2026, Black Rock)

First actual measurement rather than theory, from `tools/px4_health_report.py` with the aircraft
parked and disarmed:

| Reading | Value | Verdict |
|---|---|---|
| PX4 warnings in 25 s | none | no yaw or GPS error firing |
| GPS | 3D fix, 10 satellites, eph 0.7 m, epv 1.1 m | inside `EKF2_REQ_EPH 3` and `EKF2_REQ_EPV 5` |
| Attitude | roll +0.006, pitch -0.004, yaw 1.551 rad | steady, level |
| Vibration | 0.00 on all axes | nothing |
| `EKF2_MAG_DECL` | 12.99 deg | matches Black Rock's true declination of 12.82 deg (IGRF) |
| `EKF2_MAG_TYPE` | 0 (automatic) | default |
| `SENS_EN_MAGSIM` / `GPSSIM` / `ARSPDSIM` | all 1 | confirms the sensors are simulated inside PX4 |

The `SENS_EN_*SIM` values confirm the retraction above from the running system, not just from the
source: these sensors do not come from Gazebo.

**So the estimator is healthy on the ground.** The yaw and GPS-drift warnings seen earlier are
transient start-up messages that clear, not a standing fault - which also means they are not the
explanation for erratic flight, and chasing them further would be a fourth wrong turn.

**The problem is in the air, and has never been measured there.** Every diagnostic so far has been
taken with the aircraft parked. The report tool now accepts a listening duration, so the next step
is to run it across an actual flight and capture the estimator while the aircraft is misbehaving:

    python3 tools/px4_health_report.py 14550 180

**Tool defect found and fixed in passing:** integer parameters were printed as the bit pattern of
their value read as a float, so `SENS_EN_MAGSIM 1` appeared as `1.4013e-45`. PX4 sends integer
parameters that way in `PARAM_VALUE`; they are now reinterpreted by `param_type`.
