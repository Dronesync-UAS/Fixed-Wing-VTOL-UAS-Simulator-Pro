# The external view moves into the console — 11 October 2026

## Why

Seeing the aircraft meant looking at the Gazebo window. The console had a
nose camera and a plan view, neither of which shows the airframe itself, so
an instructor watching a student had to keep a second window in view and
drive its camera with **Set External View**. On a tiled screen that is half
the display spent on a window whose only job is one picture.

## What was built

A second camera sensor on the aircraft's `base_link`, nine metres behind and
2.2 m above, streamed into a **Chase Camera** panel the same way the nose
camera already is — Gazebo camera sensor → `gz-transport` → JPEG → MJPEG in
an `<img>` tag. No new mechanism; the existing one now carries two cameras.

`tools/chase_camera_apply.py` adds the sensor, with the same safety the
world tools have: backup to `model.sdf.prechase`, parse the result, restore
automatically if it breaks, `--dry-run` and `--revert`.

## Decisions

**Attached to the aircraft, not placed in the world.** A camera that follows
has to be part of the thing it follows. It banks and turns with the
airframe, which is what makes it a chase view rather than a fixed camera the
aircraft flies out of within seconds.

**The pitch is derived, not eyeballed.** The camera looks along its own +X,
so raising it 2.2 m while holding it 9 m back puts the aircraft above the
frame unless it is tilted down by `atan(2.2/9) = 0.24 rad`. The test asserts
the pose and the pitch agree, rather than that the pitch is some blessed
number — change the geometry and the test still means something.

**Small and slow on purpose.** 640×360 at 15 Hz against the nose camera's
1280×960. This is a second rendered camera on a machine whose graphics
performance is already marginal (12 July entry), and it is a situational
view, not an instrument. If the simulator slows, `--revert` removes it.

**`video_feed.py` stopped being a single camera.** It held one topic, one
latest frame and one watchdog at module level. Adding a second camera by
copying the file would have left two watchdogs to drift apart, so the state
moved into a `CameraFeed` instance; the module-level functions stayed as
thin wrappers so the station and the environment plugin did not change.

**The link and sensor names live in one place.** `sim_target.CHASE_CAMERA`
holds them, the tool writes them into the model, and the station builds its
subscription topic from them. They are the only thing joining the two
halves, and a rename on one side would fail silently — the panel would just
show nothing — so the test asserts the topic the station would subscribe to
matches the sensor the tool actually wrote.

## Testing

`tools/test_chase_camera.py` runs the tool against a stand-in `model.sdf`
with the awkward bits real files have: single-quoted link names, an existing
nested sensor, and a `</link>` that is not the first in the file. It checks
the sensor lands in `base_link` and not in `rotor_0`, that the existing IMU
survives, that the camera is behind and above and pitched to match, that it
sees past the 500 m operating limit, that it is as small and slow as
claimed, that the topic matches `sim_target.chase_camera_topic()` exactly,
that re-running skips, that `--revert` restores the file byte-for-byte, and
that a model with no `base_link` is refused rather than half-edited. All
pass. `tools/offline_render_check.py` passes with the new panel.

**Not yet run against Gazebo.** Nobody has seen the picture, and what the
second camera costs in frame rate on this machine is unknown. That is the
first thing to find out, and the reason `--revert` is documented in the
tool's own output rather than buried here.
