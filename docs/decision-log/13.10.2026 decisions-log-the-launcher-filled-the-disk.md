# 13 Oct 2026 - The launcher filled the disk with a prompt

## What was found

`~/uas_sim_logs/sim_launch.log` was **19.5 GB**. It had been 4 GB at 00:57
the same day, so roughly 15 GB arrived during one day's running.

Sampled at a quarter, a half and nine tenths of the way through, the file
is the same thing everywhere: the escape sequence that clears a terminal
line, followed by `pxh> `, over and over, with no newlines at all. The
whole file is PX4's shell prompt being redrawn.

## Why

`tools/uas_launcher.py` started PX4 with `stdin=subprocess.DEVNULL`.

`/dev/null` returns end-of-file on the first read. PX4's own shell treats
that as "the line ended", prints a fresh prompt and reads again - and the
next read ends immediately too. It is a loop with nothing to slow it down,
and every pass writes a prompt into the log.

`tools/start_world.sh` has never shown this, which is why it went
unnoticed: it runs in a terminal, and a terminal's stdin BLOCKS rather
than ending. So the two ways of starting the simulator were not the same,
and only the one behind the desktop icon - the one an instructor actually
uses - had the fault.

Measured directly rather than argued:

    stdin=DEVNULL                         end-of-file in 0.00 s
    pipe, write end held by the child     blocks, as a terminal does

## The fix

The launcher now hands PX4 a pipe and passes the WRITE end to the child.
A pipe with a writer still attached never reaches end-of-file, so the read
waits - exactly what a terminal does.

The write end goes to the child rather than being kept by the launcher on
purpose: the launcher exits once everything is up, and anything it held
would close with it and bring the loop straight back.

`tools/test_launcher.py` section 11 checks the behaviour rather than the
source, because the source reads reasonably either way - `DEVNULL` looks
like the careful choice, and it is the one that filled the disk. It
asserts that `/dev/null` really does end at once, that the pipe does not,
and that `start_simulator` uses the pipe.

## What was done about the file

Truncated in place rather than deleted: the running simulator still held
it open, and unlinking an open file frees nothing until the last process
exits. 18 GB came back immediately (347 GB free to 365 GB).

The launcher opens the log with `"w"`, so it is already truncated at every
launch. The runaway was always within a single session.

## Not yet confirmed

The fix is proven in isolation, with a stand-in process that reads a line
and reports whether it got end-of-file. It has NOT yet been seen against a
real PX4 start - that needs a launch from the desktop icon, and the check
afterwards is simply whether the log is still a few kilobytes.
