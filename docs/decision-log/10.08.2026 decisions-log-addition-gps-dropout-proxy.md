GPS Dropout Proxy — built and confirmed working (10 August 2026)

Built and tested a working method for simulating GPS failure for instructor-triggered malfunction training, replacing reliance on PX4's built-in failure injection (previously found broken — see prior entry re: PX4 GitHub issue #22296).

**Problem being solved:** PX4's built-in `MAV_CMD_INJECT_FAILURE` GPS command is accepted and acknowledged but has no visible effect in QGroundControl — a known, unfixed PX4 bug. This blocks CAP722B 5.5(l) (GPS performance modelling, nominal/degraded).

**Approach:** Built a standalone Python "proxy" program (`gps_dropout_proxy.py`, stored in `instructor_panel`) that sits between PX4 and QGroundControl. It passes all normal telemetry through untouched, but when the instructor types "fail", it rebuilds the GPS status message with satellite count and fix quality zeroed out before forwarding to QGroundControl — and restores normal values on "restore".

**Confirmed working end-to-end:** QGroundControl's displayed satellite count and GPS status genuinely change when triggered — first real (non-buggy) GPS failure simulation for the simulator.

**Setup required (currently manual, three steps, done in this order after PX4/Gazebo/QGroundControl are all running normally):**
1. In the PX4 console (`pxh>` prompt), stop the default telemetry stream to QGroundControl by its local port (found via `mavlink status` — NOT necessarily always port 18570; check current instance list each time, as PX4 assigns these per session):
   `mavlink stop -u <local_port>`
2. Start a replacement stream aimed at the proxy instead of QGroundControl directly:
   `mavlink start -u <same_local_port> -o 14555 -t 127.0.0.1`
3. Run the proxy script from a terminal in the `instructor_panel` folder:
   `python3 gps_dropout_proxy.py`

QGroundControl reconnects automatically once the proxy is running (still using its normal autoconnect on port 14550 — confirmed via Application Settings → Comm Links → AutoConnect that no manual link is configured).

**Technical issues hit and fixed during build (documented for future reference / anyone extending this script):**
1. First `mavlink stop -u 14550` attempt failed — the port number needed is PX4's own local port for that stream (found via `mavlink status`), not the remote/destination port.
2. Script originally crashed with `NotImplementedError: MAVLink_message cannot be serialized directly` — caused by forwarding a received message object directly through a second, separate connection; the two connections don't reliably agree on how to re-package a message that originated on the other one. Fixed by: passing untouched messages straight through as raw bytes (`get_msgbuf()`), and rebuilding only the GPS status message from scratch using the outgoing connection's own message-building function.
3. After that fix, the rebuilt GPS message was being sent but QGroundControl wasn't reacting to it — root cause was the rebuilt message being labelled with the proxy's own default identity rather than the real aircraft's system ID, so QGroundControl likely wasn't attributing it to the tracked vehicle. Fixed by copying the real aircraft's system/component ID onto the rebuilt message before sending.

**Not yet done — required before this is a finished feature, not just a proven prototype:**
- Steps 1–3 above are manual and must be automated (ideally into one script/button) rather than typed by hand each session.
- Not yet wired into the instructor control panel itself — currently triggered by typing "fail"/"restore" into a terminal, not a button alongside freeze/reposition/malfunction injection.
- Failure behaviour is currently instant and total (all satellites to zero immediately). Whether that's the right training behaviour, versus a gradual degradation, is an open question for the Head of Training — not decided.
- No automatic logging yet of when GPS failure is triggered/restored. Flagged as a natural, low-effort addition once the above is finalised — would give a ready-made timestamped record for instructor assessment purposes, per the standing assessment-logging requirement.
